# Validación local H5 de Axel Cueva

Ejecutar desde la raíz de Backend, con las dependencias del lockfile y un checkout de Docs en la revisión que se quiere medir. Las herramientas de evidencia consumen exportaciones depuradas. Los JSON crudos con credenciales, cabeceras, payloads comerciales o identificadores de infraestructura deben permanecer fuera de este directorio.

El preflight resuelve los SHAs de Backend y Docs y lee todos los archivos inspeccionados directamente desde Git (`git show <sha>:<ruta>`), nunca desde el árbol de trabajo en disco. Acepta un ref de Docs como segundo argumento y un ref de Backend como tercero (ambos por defecto `HEAD`).

Las pruebas deterministas de **SEC-CD-01**, **CD-06**, **CD-07**, **Preflight**, **PERF-05** y **RL-05** forman parte del job obligatorio `azure_cd_h5` en `.github/workflows/ci.yml`, consolidado en `integral` y `compatibilidad`. Se ejecutan sin llamadas a Azure, credenciales reales, proveedores externos ni aprovisionamiento, separadas de los benchmarks reales (`performance-g6.yml`).

## Formatos observados

- **Recibo de despliegue Chile**. Coloca el JSON emitido por `deploy.sh` en `receipt` sin editarlo. El validador usa `workflow_run_id`, `origin_https` y `previous` para vincular el recibo al mismo run, al smoke y a la imagen anterior. El SHA se verifica mediante la procedencia de la imagen vinculada al digest del recibo. Un recibo oficial por sí solo no acredita una recuperación ni identifica la revisión anterior.

- **SEC-CD-01**. `verify-release-evidence.mjs <observacion.json>` evalúa un export confiable y sanitizado exclusivamente del carril Chile (`destination: "chile-shared"`, `environment.name: "azure-h5-chile"`, `aca_environment: "env-g6-phase1-chile"`). Lee `ops/azure/container-apps/deployment-targets.json` y `ops/azure/container-apps/verify-environment-protection.sh` como fuentes oficiales: Castilla (`mrcastilla8`, id `143348512`) como único revisor, autoaprobación autorizada (`prevent_self_review: false`), `admin_bypass: false` y despliegues únicamente desde la rama `master`. Conserva las verificaciones de SHA, digest, OIDC, recibo del mismo run, auditoría `npm`, smoke y recuperación. El [fixture de referencia](verify-release-evidence.test.mjs) muestra casos positivos (incluida autoaprobación válida por Castilla) y negativos. La infraestructura existente de Brasil se conserva intacta fuera del alcance de esta validación de entrega Chile.
- **PERF-04**. El fixture loopback (`PERF04_PROFILE=fixture` con `PERF04_SYNTHETIC_FIXTURE=1`) valida únicamente el flujo contractual de admisión (`202`), replay idempotente (`200`), conflicto de idempotencia (`409`) y consulta terminal (`COMPLETED`/`REJECTED`). Su salida JSON (`handleSummary`, escribible vía `PERF04_SUMMARY_PATH`) declara explícitamente `execution_kind: "SYNTHETIC_LOOPBACK_CONTRACT_CHECK"`, `evidence_level: "L0_SYNTHETIC_LOOPBACK_FIXTURE"`, `certification_status: "NOT_CERTIFIED"` e `is_release_measurement: false`, y separa los tiempos sintéticos de loopback para impedir que se presenten como throughput, p95 de release o certificación de rendimiento.
  - **Requisitos de certificación:** mediciones reales contra un ambiente autorizado y un dataset controlado y previamente sembrado (`PERF04-*`, base nueva por corrida, 3 repeticiones baseline/candidato en perfiles `smoke`/`small`/`medium` de `hitos/h5/03_PRUEBAS_DE_PERFORMANCE.md`), alcance N01 habilitado en el release y conciliación de backlog/cuota con PostgreSQL y telemetría del mismo run.
  - **Dependencia externa y punto de integración (Vera):** la definición de umbrales de rendimiento aprobados (`SIN_UMBRAL_APROBADO` en `scripts/performance/summarize-selection.mjs`) y la interfaz del runner común k6 permanecen bajo coordinación de **Vera**. El punto exacto de integración es `apps/promotions-svc/test/performance/coupon-admission.k6.js` (variables `PERF04_ORIGIN`, `PERF04_TEST_TOKEN`, `PERF04_SYNTHETIC_DATASET`, `PERF04_PROFILE`, `PERF04_SUMMARY_PATH`; bloque `options.thresholds` para incorporar los umbrales de latencia/RPS que Vera apruebe; y salida estructurada de `handleSummary`).
- **PERF-05**. `node ops/azure/service-bus/summarize-observations.mjs <observacion.json>` usa una ventana UTC (`start_utc`, `end_utc`), `complete_capture` y conjuntos explícitos de `outbox`, `attempts` y `samples`, como en el [fixture](../../service-bus/summarize-observations.test.mjs). Normaliza una fila por intención `(producer, event_id, destination)` y correlaciona por `(destination, message_id)`, `operation_id` y productor. Ordena los intentos por `delivery_count` para admitir observaciones fuera de orden y valida cobertura completa: si `complete_capture` no es `true`, si el primer intento observado comienza en `delivery_count > 1` sin acreditar entregas previas, si existe un salto en `delivery_count` o si faltan observaciones de entrega, informa el motivo exacto (`TRUNCATED_CAPTURE`, `UNCONFIRMED_CAPTURE_COMPLETENESS`, `MISSING_INITIAL_DELIVERY_ATTEMPT`, `DELIVERY_COUNT_GAP`, `MISSING_DELIVERY_OBSERVATIONS`), deja las métricas afectadas como inconclusas (`null` / `status: "INCONCLUSIVE"`), marca `certification_eligible: false` y devuelve código de salida `2`. El código `0` indica que la captura es completa. Para obtener `certification_eligible: true`, la captura debe ser completa y el export de una fuente confiable debe identificar `environment: "azure"` y `destination: "chile-shared"`. Las capturas sintéticas y aisladas conservan sus métricas de prueba.
- **RL-05**. `node ops/azure/tests/h5-rl/verify-rate-limit.mjs <trazas.json>` recibe `run_id`, `start_utc`, `end_utc` y los cinco conjuntos (`offered`, `apim`, `gateway`, `provider`, `direct`) del [fixture](../h5-rl/verify-rate-limit.test.mjs). Cada registro de traza en todas las capas debe incluir `run_id` coincidente y `observed_utc` dentro de `[start_utc, end_utc]`; cualquier identificador distinto, timestamp fuera de ventana o metadato ausente/inválido se rechaza de forma explícita. Conserva la verificación por correlación de UUID que garantiza que los requests rechazados con `429` en APIM no aparecen en Gateway ni en el proveedor. `complete_capture: true` requiere constancia de captura completa y sin muestreo en los tres puntos. Castilla e Infra aportan política, origen privado y trazas sanitizadas de Azure.

Las pruebas del ejecutor requieren Bash y jq. `CD-06` comprueba que el gate rechaza un informe ausente, inválido o con vulnerabilidades altas o críticas aunque el escáner salga con código 0. `CD-07` comprueba para las nueve aplicaciones que el JSON de liveness (`/health`, `status: "ok"`) y readiness (`/health/ready` o `/health/readiness` según contrato, `status: "ready"`; sin readiness HTTP para `api-gateway`) identifica al servicio esperado y rechaza HTTP 200 con identidad o estado incorrecto. La validación del despliegue protegido requiere una ejecución autorizada del CD en Chile.
