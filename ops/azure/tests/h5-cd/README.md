# Validación local H5 de Axel Cueva

Ejecutar desde la raíz de Backend, con las dependencias del lockfile y un checkout de Docs en la revisión que se quiere medir. Las herramientas de evidencia consumen exportaciones depuradas. Los JSON crudos con credenciales, cabeceras, payloads comerciales o identificadores de infraestructura deben permanecer fuera de este directorio.

El preflight acepta un ref de Docs como segundo argumento. Usa `origin/master` para leer ese commit sin cambiar el checkout.

## Formatos observados

- **SEC-CD-01**. `verify-release-evidence.mjs <observacion.json>` evalúa un export confiable y sanitizado del carril `azure-h5`. Usa aprobaciones, identidad OIDC, informe de npm, resultado HTTP y recibo correspondientes al mismo run, SHA y servicio. El [fixture de referencia](verify-release-evidence.test.mjs) muestra la forma. El validador estricto es local. El CD oficial se comprueba por separado.
- **PERF-04**. `k6 run --summary-export=resultado.json apps/promotions-svc/test/performance/coupon-admission.k6.js` recibe `PERF04_ORIGIN` HTTP loopback, `PERF04_TEST_TOKEN`, `PERF04_SYNTHETIC_DATASET` y `PERF04_PROFILE` (`smoke`, `small`, `medium`). Cada fila del dataset contiene `body` con un pedido `PERF04-*` previamente sembrado, `conflict_coupon_code` distinto y `expected_terminal`. Un pedido y UUID por iteración, con la misma clave para replay y conflicto. El laboratorio debe usar una base nueva por corrida, con la reserva y el cupón sembrados por el flujo autorizado. Los contadores k6 miden intentos, admisiones, replays, conflictos, 5xx y resultados; el backlog y la cuota se concilian con PostgreSQL/telemetría del mismo run. Vera controla la integración al runner común y las comparaciones baseline/candidato.
- **PERF-05**. `node ops/azure/service-bus/summarize-observations.mjs <observacion.json>` usa una ventana UTC y un conjunto explícito de `outbox`, `attempts` y `samples`, como en el [fixture](../../service-bus/summarize-observations.test.mjs). Normaliza una fila por intención `(producer, event_id, destination)` y correlaciona por `(destination, message_id)`, `operation_id` y productor. `enqueued_utc` se obtiene de la observación del broker o queda `null` si sigue pendiente. Las muestras incluyen ambos límites de la ventana. Conservar la fuente exigida de commits y settlements. Las latencias sin muestras devuelven `null`. El drenaje es la estimación desde la primera muestra ocupada hasta la muestra sin backlog ni Outbox pendiente.
- **RL-05**. `node ops/azure/tests/h5-rl/verify-rate-limit.mjs <trazas.json>` recibe los cinco conjuntos del [fixture](../h5-rl/verify-rate-limit.test.mjs). Usar un UUID por intento, al menos un control admitido, un 429 en el borde y una solicitud directa denegada, todos observados en la misma ventana. `complete_capture: true` requiere constancia de captura completa y sin muestreo en los tres puntos. Castilla e Infra aportan política, origen privado y trazas sanitizadas de Azure.

Las pruebas del ejecutor requieren Bash y jq. `CD-06` comprueba que el gate rechaza un informe ausente, inválido o con vulnerabilidades altas o críticas aunque el escáner salga con código 0. `CD-07` comprueba que el JSON de liveness y readiness identifica al servicio esperado. Las pruebas usan respuestas sintéticas y documentan la protección del código. La validación del despliegue protegido requiere una ejecución autorizada del CD.
