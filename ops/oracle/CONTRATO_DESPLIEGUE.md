# Base documental de desarrollo y despliegue G6 (propuesta, no contrato definitivo)

> Esta estructura de `ops/oracle/` está aprobada como base documental, pero no está aprobada como contrato definitivo de desarrollo/despliegue. Las fichas y requisitos sirven para preparar microservicios; los conflictos identificados, especialmente RabbitMQ, son bloqueos específicos y no deben convertirse en acuerdos por inferencia. El estado por SHA está en [ESTADO_SERVICIOS.md](ESTADO_SERVICIOS.md).

**Alcance:** preparación técnica de los nueve componentes para el sistema Oracle existente. No concede autorización de despliegue ni cambia los contratos externos. Estado VM: observación `2026-10-19 22:32:52–22:36:19 UTC`, [ESTADO_ACTUAL.md](ESTADO_ACTUAL.md). Fuente de despliegue: `services.psv` registry v2, Compose de `ops/oracle/`, `Dockerfile.service`, `ops/oracle/build-service.sh`, workflows de `.github/workflows/` y código de cada servicio en el SHA de esta rama. Contratos oficiales consultados en docs `origin/master` SHA `c36bd9a18f4fdb188df0d7e5158a431cf4b4ea7b`: OpenAPI `0.6.0-rc.1`, AsyncAPI `0.6.0-rc.2` (candidatos; consultar su estado documental, no inferir homologación externa). Las ramas personales no fusionadas se citan como evidencia de implementación pendiente, nunca como contrato.

## Obligaciones verificables

| Regla | Evidencia normativa / verificación de desarrollo |
|---|---|
| Runtime compatible con Node `^22.22.3 || >=24.15.0`, npm `>=10`; imagen de CI/producción pinneada a Node `24.15.0-alpine` por digest. | `package.json`, `.nvmrc`, `.node-version`, `Dockerfile.service`, `Dockerfile.inventory-svc`. Build local con `npm ci` y script de build listado en `services.psv`. |
| Cada servicio usa el puerto del registro y ambas variables `PORT` + variable específica; no publicar a interfaz externa. | `ops/oracle/services.psv`, Compose base; mapping observado `127.0.0.1:3000–3008`. Cada `main.ts` acepta variable específica/`PORT`; verificar por servicio. |
| Cada servicio debe producir su `dist/apps/<servicio>/main.js`. La imagen `Dockerfile.service` ejecuta `dist/apps/g6-service-entrypoint.mjs`, wrapper generado por `ops/oracle/build-service.sh` a partir de `main_module`; la imagen dedicada `Dockerfile.inventory-svc` ejecuta directamente `dist/apps/inventory-svc/main.js` y no requiere ni copia ese wrapper. Validar el artefacto y CMD efectivos del Dockerfile utilizado. | `services.psv`, Dockerfiles, workflow CI y `ops/oracle/build-service.sh`. El script genera el wrapper genérico; no implica que Inventory lo consuma. La compilación por sí sola no acredita funcionalidad. |
| Producción debe arrancar `NODE_ENV=production`, como usuario no root en imagen genérica, con configuración validada al bootstrap y sin fallback silencioso. | `Dockerfile.service`, Compose. Configuración del servicio ficha correspondiente. Variables secretas solo por runtime privado. |
| Liveness HTTP `GET /health` devuelve 200 solo si proceso sirve; Compose genérico chequea ese path, Gateway ejecuta `dist/apps/api-gateway/readiness.js`. Liveness no es readiness. | Compose y Dockerfile; controllers por aplicación. Mantener `GET /health` sin dependencias y readiness separada, real y observable para dependencias imprescindibles. |
| Readiness responde no listo si una dependencia esencial no puede sostener las operaciones del servicio. No declarar listo por health, mock o respuesta fija. | Código readiness/health y CI smoke. Registra dependencia y prueba real. Oracle observó Catalog readiness 503 y Gateway unhealthy al 19-oct-2026. |
| Apagado ordenado: manejar señales del runtime, cerrar listener, pool PostgreSQL, consumidores Rabbit y worker/outbox que posea el servicio; no terminar procesos secundarios huérfanos. | Ciclo de vida NestJS y adapters. Solo exigir cierre de recursos realmente inicializados. La implementación debe tener test de shutdown para los recursos que incorpora. |
| PostgreSQL: TLS validado con CA montada como `/run/g6-certs/supabase-server-root.crt` de solo lectura; credencial/rol por servicio y mínimo privilegio, schema aislado. | Compose genérico y overlay Inventory; código DB del servicio; migraciones/schema oficiales. Oracle muestra montaje CA ro en cuatro web containers, pero no se leyeron runtime env. No conceder permisos ni inferir el rol de una URL. |
| No aplicar migraciones destructivas ni migraciones de producción en el arranque. | Reglas backend `AGENTS.md`, scripts de migración de servicio y decisiones de persistencia. Preparar migraciones aditivas reversibles y proceso aparte; SQL a Supabase requiere autorización explícita de Marco. |
| HTTP entre servicios solo por `g6-http`, con alias verificado; Gateway es el único G6 conectado también a `g6-edge`. Caddy habla con Gateway en `g6-edge`. | Compose y auditoría 19-oct. Configurar upstream solo cuando el destino esté autorizado, desplegado y readiness funcional. No usar `localhost` para otro contenedor. |
| RabbitMQ: usar vhost, exchanges, queue, routing key, ACK y permisos compatibles con el AsyncAPI/topología acordada y la VM. | [RABBITMQ_COMPATIBILIDAD.md](RABBITMQ_COMPATIBILIDAD.md). Actualmente Rabbit vive en bridge aislado y no hay conectividad desde redes HTTP; no hay autorización documentada para conectarlo. Bloqueo específico para los flujos AMQP. |
| Auth JWT/JWKS y roles/scopes deben corresponder al OpenAPI y DEC-F aplicable; `GATEWAY_DEMO_NO_AUTH_ENABLED` o flags demo no se convierten en excepción de producción. | Contrato oficial y configuración de Gateway/servicio. Demo sin auth solo en entorno segregado y con guard explícito del código. No inventar scope ni atribuir permisos externos. |
| Clientes HTTP/AMQP usan timeout acotado, clasificación de errores, retries limitados solo si están contractualmente definidos; escrituras idempotentes. | OpenAPI, AsyncAPI, decisiones/ADR aplicables y código. Outbox/Inbox solo cuando lo exijan el caso y contrato adoptado. No agregar retry/DLX por analogía. |
| No usar mocks, repositorios no configurados o datos de demo en runtime productivo para simular un upstream o base caídos. | Configuración de production y bootstrap. Tests unitarios pueden usar dobles, claramente confinados a pruebas. |
| Probar dependencias reales de forma aislada, no contra Oracle compartido durante desarrollo. | `package.json`, workflows CI, scripts `scripts/ci/`, Compose. PostgreSQL desechable/TLS; Rabbit local aislado solo con nombres y topology aprobados. Sin interacción destructiva contra VM. |
| Una release es por SHA inmutable, servicio individual, autorización individual. Readiness y smoke deben corresponder al SHA candidato. | Workflow CD, `services.psv`, `auto-release-authorization.psv`, `ops/oracle/README.md`. Autorizaciones automáticas son `false` para los nueve servicios según el estado comprometido. |

## Evidencia por cambio

Adjuntar en el PR/issue: SHA, rama y owner; contratos/versions que aplica; salida de build, typecheck, lint, tests; lista de variables con fuente/categoría (sin valores); resultado de PostgreSQL/TLS/Rabbit real aislado si aplica; `docker compose config --quiet` y build de imagen; smoke health/readiness y al menos un flujo funcional de lectura/escritura seguro; dependencias no comprobadas y criterio de desbloqueo. El checklist define estados y plantilla. Unit tests por sí solos nunca prueban disponibilidad de Oracle ni readiness externa.
