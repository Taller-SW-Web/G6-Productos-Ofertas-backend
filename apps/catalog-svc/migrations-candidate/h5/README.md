# Candidato H5 para Catalog

El módulo `catalog-service-bus.ts` consume mediante Peek-Lock y completa tras el retorno del caso de uso de Catalog. El handler usa el Inbox existente. Fallas transitorias abandonan la entrega y validaciones del sobre se envían a DLQ. Un fallo al completar puede causar redelivery con la misma identidad. La autorización de Azure depende del permiso de escritura exclusivo sobre cada cola de origen. El atributo `producer` y los metadatos se cotejan como controles de integridad.

El trigger de `0001_outbox_delivery.sql` materializa una entrega por destino autorizado dentro de la misma transacción que inserta el Outbox; no hay una ruta de inserción manual. La clave `(message_id, destination)` evita duplicados. `relayCatalogDelivery` confirma una entrega por intento y no actualiza `catalog.outbox.published_at`. El lease con token evita que un worker atrasado confirme la entrega de otro. La llamada de red ocurre después del commit del claim. Una respuesta ambigua conserva el mensaje y permite reintentar con el mismo ID. El índice parcial cubre el barrido de pendientes.

El runtime Catalog H5 se selecciona con `MESSAGING_PROVIDER=AZURE_SERVICE_BUS` y `SERVICE_BUS_NAMESPACE_FQDN`; inicia receptores para Taxonomy, Bulk, Pricing e Inventory. `CATALOG_H5_DESTINATIONS` es la lista explícita de destinos salientes autorizados y su valor predeterminado es vacío. En producción exige `AZURE_CLIENT_ID`, `G6_SECURITY_MODE=G7_AUTHENTICATED` y `G6_SERVICE_BUS_PRODUCTION_ENABLED=true`. RabbitMQ sigue como transporte H4 cuando H5 no está seleccionado; ambas opciones no pueden ejecutarse juntas.

La migración candidata `0001_outbox_delivery.sql` instala la tabla de entregas y el único trigger que hace fan-out transaccional según el proveedor y los destinos autorizados guardados con `set_config(..., true)`. `0002_taxonomy_reply_transport.sql` marca las filas H5 para que el relay H4 no las publique y conserva el marcador explícito de respuestas R18/R09. Ejecutar ambas solo en PostgreSQL 17 descartable hasta completar revisión; no aplicarlas a Supabase compartido.

La columna `catalog.outbox.delivery_transport` mantiene `RABBITMQ` como valor por defecto para filas históricas y nuevas transacciones H4. El trigger `trg_catalog_taxonomy_reply_transport` corre antes de cada inserción y cambia a `AZURE_SERVICE_BUS` cualquier evento escrito en una transacción cuyo proveedor sea `catalog.messaging_provider = 'AZURE_SERVICE_BUS'`; también conserva el marcador explícito `g6.catalog_taxonomy_reply` para las respuestas R18/R09. El trigger canónico de fan-out de `0001_outbox_delivery.sql` sigue siendo el único escritor de entregas: la allowlist produce una fila por destino autorizado y una lista vacía produce cero filas. El relay H4 filtra `delivery_transport = 'RABBITMQ'`, por lo que un evento H5 no se publica accidentalmente por RabbitMQ cuando el proceso vuelve a H4, aunque no tuviera destinos H5 o ya se hayan publicado sus entregas.

Las migraciones candidatas `0001_outbox_delivery.sql` y `0002_taxonomy_reply_transport.sql` requieren el schema y el rol `catalog_app` ya instalados. La segunda se ejecuta después de la primera y marca todos los eventos insertados dentro de transacciones H5, además de conservar el marcador explícito en las respuestas R18/R09. La marca y las entregas se escriben en la misma transacción que el hecho de negocio, la barrera y el Inbox cuando corresponda. El publicador H4 omite estas filas, incluso al regresar a H4. El modo de prueba `-IncludeH5` del script `docs/hito-4/probar-catalogo-postgres.ps1` la carga en una base descartable con PostgreSQL y TLS, y ejecuta el relay contra un emisor simulado. Antes de activar H5, detener las réplicas de Catalog con el publicador H4 anterior a la marca, y drenar o conciliar sus respuestas pendientes. El retorno a H4 requiere congelar los escritores H5 y conciliar entregas por ID, Inbox y resultado de negocio antes de decidir el destino de los pendientes. Retener la tabla como evidencia hasta completar la conciliación.

El candidato requiere colas preaprovisionadas, límites Basic verificados, identidad administrada, RBAC por cola y acuerdos de consumo. Los mensajes Bulk demasiado grandes requieren fragmentación semántica o claim-check antes de la activación. Una expiración en el broker requiere conciliación por ID original y autorización de replay.

La migración candidata `0003_bulk_retry_receipts.sql` agrega recibos durables por operación de fila e intento para BULK_RETRY_V1. Se aplica después de `0002_taxonomy_reply_transport.sql` en PostgreSQL descartable; no ejecutar en Supabase compartido sin aprobación de operación.
